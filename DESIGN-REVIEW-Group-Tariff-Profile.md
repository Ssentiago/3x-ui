# Дизайн-оценка фичи Group / Tariff / Profile

## Резюме

Фича вводит трёхуровневую модель **Profile → Tariff → Group** для управления политиками клиентов (трафик, экспирация, IP-лимиты, инбаунды). Это значительное улучшение по сравнению с предыдущей системой "текстовое поле group", но имеет несколько архитектурных проблем, требующих внимания.

---

## Сильные стороны

### 1. Чёткая доменная модель

Иерархия Profile → Tariff → Group → Client логична и выражает намерение администратора на трёх уровнях абстракции:
- Profile — переиспользуемый кирпич (50GB + 30 дней)
- Tariff — композиция профилей + стратегии слияния
- Group — применение тарифа к клиентам

### 2. Read-time resolution (вместо денормализации)

Ключевое архитектурное решение: значение не хранится на клиенте, а вычисляется при каждом чтении. Это даёт:
- мгновенное применение изменений тарифа ко всем клиентам
- отсутствие дрифта между "источником истины" (тариф) и "исполнением" (клиент)
- чистую семантику: NULL = не участвует, 0 = безлимит

### 3. Стратегии слияния по полям

overwrite/sum для трафика, overwrite/union для инбаундов — практичное решение, учитывающее природу данных.

### 4. Override-система с двусторонним переключением

"make local" / "return to tariff" — хороший UX-паттерн. Клиент не теряет связь с тарифом навсегда. Приоритет override > tariff chain > client default прост и предсказуем.

### 5. Переиспользуемость профилей

Профиль "Base 50GB/30d" может быть стартовой точкой для Silver, Gold, Platinum — снижает дублирование и упрощает массовые изменения.

### 6. Resolved preview в модалке тарифа

Оператор видит итоговые значения до сохранения — правильный паттерн для превентивной валидации.

### 7. Защита от удаления при наличии ссылок

Профили нельзя удалить пока тариф их использует, тарифы — пока группы привязаны. С перечнем зависимых.

## Проблемы дизайна

### 1. Три параллельных реализации резолвера — архитектурный долг (High)

Go, SQL-выражения, TypeScript. Две из трёх покрыты тестами, но TS-резолвер (`frontend/src/lib/tariff/resolveChain.ts`) не тестирован.

- Риск рассинхронизации: любая правка логики должна отражаться в трёх местах
- SQL-резолвер наименее читаем и наиболее хрупкий — если стратегия слияния усложнится, SQL станет неуправляемым
- TS-резолвер используется только для превью в модалке, что создаёт иллюзию "только для UI", но на деле это третья копия бизнес-логики

**Рекомендация:** рассмотреть генерацию резолвера из описания (DSL или code-gen из Go), либо свести к одной серверной реализации с API-вызовом для фронта. Как минимум — добавить TS-тесты, которые гоняют ту же матрицу кейсов что и Go-тесты.

### 2. NULL vs 0 vs [] — классический источник багов (High)

Различие `NULL` ("не высказывается") и `0` (unlimited) и `[]` (пустой список) — корректно в Go через `*int64`, но:

- Любой `omitempty` в JSON-сериализации сольёт `NULL` и `0` в `0`. Нужна явная типизация через `*int64` + кастомная сериализация
- В API-схемах это легко пропустить — фронтенд может отправить `0` вместо `null` при пустом поле
- Для инбаундов: разница между `[1,2]` (конкретный список), `[]` (пустой список = без инбаундов) и `null` (не участвует) критична. Если оператор случайно отправит `[]` вместо `null` в профиле — все инбаунды ниже по цепочке при `overwrite` стратегии будут перезатёрты пустым списком

**Рекомендация:** зафиксировать в OpenAPI-схеме strict nullable через `type: integer, nullable: true`. В Zod-схемах использовать `.nullable()` с явной валидацией. Добавить интеграционный тест: профиль с `null` traffic → JSON → Go struct → `*int64(nil)` (не `*int64(0)`).

### 3. Expiry anchored to `tariff_started_at` — неявная сложность (Medium)

Экспирация считается от `tariff_started_at`, который перевыставляется при:
- вступлении клиента в группу
- смене тарифа у группы
- bulk-add в тарифную группу

- Неясная семантика для админа: "30 дней от чего?" — от создания клиента? от присоединения к группе? от последнего изменения тарифа?
- Reset traffic vs. reset expiry: при сбросе трафика нужно ли сбрасывать `started_at`?
- Пересечение с delayed start: упомянута обработка "expiry/delayed-start interplay" в ClientFormModal

**Рекомендация:** вынести `tariff_started_at` в явное поле в форме клиента (read-only), чтобы админ видел точку отсчёта. Документировать семантику в UI tooltip.

### 4. `inbounds_override` как флаг вместо полноценного override (Medium)

Для инбаундов используется специальный флаг `inbounds_override *int`, потому что список инбаундов хранится в join-таблице, а не в колонке.

- Асимметрия: для scalar-полей override — это значение в колонке, для инбаундов — флаг + отдельный механизм
- При `returnToTariff` для инбаундов требуется пересоздать join-записи и перезапустить xray — дорогая и хрупкая операция

**Рекомендация:** унифицировать, хранить override-инбаунды в JSON-колонке с массивом ID, join-таблицу синхронизировать при resolve.

### 5. Position-based ordering — нет защиты от gaps (Medium)

`UNIQUE (tariff_id, position)` в БД гарантирует уникальность позиции, но:

- Нет защиты от gaps (позиция 0, 1, 3 без 2) — порядок будет некорректным
- Atomic replace через `POST /tariffs/:id/profiles` решает проблему при штатном использовании, но прямое редактирование БД или баг в миграции может создать gaps
- Нет валидации что позиции образуют последовательность `0..N-1`

**Рекомендация:** в сервисном слое валидировать что позиции образуют непрерывную последовательность. Добавить DB CHECK constraint или триггер.

### 6. Нет истории изменений тарифа (Medium)

При редактировании тарифа изменения применяются мгновенно ко всем клиентам, но:
- Нет audit trail: кто, когда, что поменял
- Нет rollback: если админ ошибся и 1000 клиентов получили `totalGB = 0` вместо 100 GB — откат только ручной
- Нет dry-run: "если я изменю стратегию трафика на sum, сколько клиентов получат больше 100 GB?"

**Рекомендация:**
- Добавить таблицу `tariff_history` (tariff_id, old_chain, new_chain, changed_by, changed_at)
- В UI тарифа: кнопка "Preview impact" перед сохранением

### 7. Асимметрия стратегий — расширяемость через миграции (Low→Medium)

Стратегии `traffic_strategy` и `inbound_strategy` хранятся как отдельные колонки на тарифе, но `expiry_days` и `limit_ip` всегда overwrite. Если понадобится `limitIp_strategy = 'min'` или любая другая стратегия для нового поля — потребуется новая колонка и миграция.

**Рекомендация:** рассмотреть хранение стратегий как JSON-объект `{traffic, inbounds, limitIp, expiry}` — расширяемо без миграций.

### 8. Unit-конверсия (GB ↔ bytes) — нечитаемые значения в API (Low)

Profile хранит traffic в GB, эффективное значение вычисляется в bytes (`<< 30`). В JSON API и UI значения будут в bytes — `644245094400` вместо `600 GB`.

- `GET /tariffs/:id` возвращает `"traffic": 644245094400` — нечитаемо для человека
- Оператор, открывший API-документацию или делающий прямой запрос, не поймёт значение

**Рекомендация:** в API-ответах отдавать и `bytes` и `displayValue` (600 GB). Или в UI всегда форматировать из bytes в человеческие единицы.

### 9. Dead columns в БД — скрытый техдолг (Low)

Legacy колонки `tariffs.total_gb`, `expiry_days`, `limit_ip`, `inbound_ids` остаются в существующих БД, но игнорируются Go-моделью.

- Оператор, заглянувший в SQLite через CLI, увидит "потерянные" данные
- Нет data-миграции для переноса старых значений в новую модель

**Рекомендация:** добавить data-миграцию (скопировать значения в profile + tariff_profiles) или хотя бы добавить комментарий в `db.go` / release note.

### 10. Отсутствие валидации цепочки профилей (Low)

- Нет проверки осмысленности: тариф из 10 профилей с `traffic = NULL` даст `totalGB` от client default — это корректно семантически, но не очевидно для админа
- Профиль можно отредактировать (хотя нельзя удалить) пока он используется — resolved значения всех тарифов-потребителей молча изменятся

**Рекомендация:** в UI тарифа показать "последнее изменение профиля X было N дней назад, затронуло N клиентов". Явно показать "from client default" в preview.

### 11. Производительность read-time resolution (Low)

Каждое чтение клиента: загрузить группу → тариф → OrderedChain профилей → walk chain → apply overrides. Для 1000+ клиентов — значительная нагрузка.

SQL-выражения (`sqlEff*`) частично решают проблему для pagination, но in-memory resolution остаётся для individual reads.

**Рекомендация:** кешировать resolved-значения на уровне тарифа (invalidated при изменении тарифа или его профилей).

### 12. UX: ManagedField не показывает resolved значение (Low)

`ManagedField.tsx` рендерит locked поле, но админ не видит resolved значение из тарифа, пока не откроет preview или эндпоинт effective.

**Рекомендация:** в форме клиента показывать resolved значение рядом с locked полем: "50 GB (from tariff Gold, profile Base)".

### 13. `RefreshTrafficForGroup*` нарушает read-time resolution (Medium)

При изменении тарифа вызывается `RefreshTrafficForGroup*`, который переписывает `client_traffics.total/expiry_time` из effective values. Это создаёт два источника истины:

- `client_traffics.total` может разойтись с resolved `totalGB` если refresh не вызвался (баг, race condition)
- Неясно, когда именно нужно вызывать refresh: при изменении тарифа? профиля? стратегии?

**Рекомендация:** задокументировать что `client_traffics` — кеш для статистики, не source of truth. Добавить invariant-checker (cron), сверяющий `client_traffics.total` с resolved `totalGB`.

## Архитектурная целостность

**Хорошо:** разделение слоёв (Model → Service → Controller → Frontend), integration points через существующие интерфейсы (ListForInbound, ToClientEffective), нет "специальных" путей для тарифов.

## Тестовое покрытие

**Сильные стороны:**
- `client_tariff_test.go`: resolve (11 случаев), override (5), effective functions (6)
- `TestSqlEffectiveMatchesGoResolver` — интеграционный тест согласованности Go и SQL резолверов

**Слабые стороны:**
- TS-резолвер не тестирован — самая хрупкая из трёх реализаций
- Нет concurrent-тестов (tariff edit + client read)
- Нет тестов для `RefreshTrafficForGroup*`
- Нет тестов для position gaps

**Рекомендация:** добавить TS-тесты для `resolveChain.ts` с той же матрицей что Go-тесты. Добавить concurrent-тест и тест RefreshTrafficForGroup.

## Итоговая оценка

**Общая оценка:** solid MVP, решающий основную проблему массового управления политиками. Цена — возросшая когнитивная нагрузка, которую нужно компенсировать в UI и документации.

**Топ-3 приоритета до production:**
1. TS-тесты для резолвера (пункт 1) — самый высокий риск рассинхронизации
2. NULL vs 0 валидация (пункт 2) — классический источник runtime-багов
3. Preview impact перед сохранением тарифа (пункт 6) — защита от массовых ошибок

**Merge-рекомендация:** merge с follow-up задачами для устранения архитектурного долга.
