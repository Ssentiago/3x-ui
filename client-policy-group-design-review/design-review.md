# Client Group Policies — Design Review

**Автор:** DeepSeek V4 Pro  
**Предметная область:** UX/архитектурный дизайн фичи  
**Ветка:** `feat/client-group-policies`  
**Дата:** 2026-07-30

---

## 1. Текущий flow

### Data model

```
Policy ──(policy_id)──► ClientGroup ──(group_name)──► ClientRecord
                                                          │
                                            inherited_from_policy (JSON)
                                            { totalGB: true, limitIP: false, ... }
```

### Пользовательский сценарий

| Шаг | Действие                             | Где                              |
|-----|--------------------------------------|----------------------------------|
| 1   | Создать Policy (шаблон настроек)     | PoliciesPage — отдельная страница |
| 2   | Создать Group + привязать Policy     | GroupsPage → модалка Create/Rename |
| 3   | Добавить клиентов в группу           | GroupsPage → Add to Group         |
|     | → авто-применение policy на клиента  | `AddToGroup` → `ApplyPolicyToClient` |
| 4   | Обновить Policy                      | PoliciesPage → Edit               |
|     | → авто-применение ко всем клиентам   | `updatePolicy` → `AutoApplyPolicyToGroups` |
| 5   | Точечный override поля у клиента     | Клиент → overrideField API        |
|     | Точечный return to policy            | Клиент → returnToPolicy API       |

### Что наследуется

- `totalGB` — квота трафика
- `limitIP` — лимит IP-адресов
- `expiryDays` — срок действия (вычисляется в `expiryTime`)
- `inboundIds` — список инбаундов

### Механика наследования

Поле `inherited_from_policy` в `ClientRecord` — JSON с флагами:
- `null` (отсутствует) → поле было унаследовано при входе в группу, можно перезаписать
- `true` → поле управляется политикой, изменения политики применяются
- `false` → поле переопределено вручную, политика не трогает

## 2. UX-проблемы

### 🔴 Проблема 1: Привязка Policy спрятана в модалку Rename

Единственный способ привязать/сменить Policy у существующей группы — открыть «Edit» (она же Rename). Юзер вынужден видеть поле имени, хотя пришёл только за политикой. Когнитивная нагрузка: «почему я должен переименовывать группу, чтобы привязать политику?»

**Влияние:** каждый чих с политикой требует лишнего клика и лишнего когнитивного шага.

### 🔴 Проблема 2: Сохранение Policy = неявный массовый apply

`POST /policies/:id/update` на каждое сохранение автоматически применяет политику ко всем клиентам во всех связанных группах. Нет preview, нет разделения «сохранить» vs «применить».

**Влияние:**
- Нельзя подготовить черновик политики
- Ошибка в одном поле → массовое изменение сотен клиентов без возможности отката
- Юзер не видит масштаб влияния до нажатия Save

### 🟡 Проблема 3: Трёхуровневый индирекшн

Policy → Group → Client. Чтобы изменить настройки группы клиентов, юзер идёт в Groups, видит имя политики, но изменить её может только через PoliciesPage — другой экран.

**Влияние:** переключение контекста для одной задачи. Юзер думает «хочу изменить настройки этой группы» — идёт не туда.

### 🟡 Проблема 4: PoliciesPage не показывает количество затрагиваемых клиентов

Колонка `groupCount` показывает количество групп. Но не клиентов. Юзер не знает, на скольких людях отразится изменение политики.

### 🟡 Проблема 5: Per-client override — отдельный API, не встроен в UI клиента

`overrideField` / `returnToPolicy` — отдельные POST-эндпоинты. В форме редактирования клиента нет индикации «это поле управляется политикой» и нет inline-переключателя «переопределить / вернуть».

## 3. Альтернативные архитектуры

Исходные ограничения:
- **Главная сущность — Client** (миграция сделана до вас, не трогаем структуру Client)
- **Не перетягивать одеяло** (Policy не должна конкурировать с Client за владение настройками)

### Вариант A: Текущий — Policy как параллельная сущность с наследованием

```
Policy ──► ClientGroup ──► Client.inherited_from_policy (JSON)
```

| Плюсы                                     | Минусы                                           |
|-------------------------------------------|--------------------------------------------------|
| Переиспользование политик                 | Трёхуровневый индирекшн                          |
| Авто-синхронизация при изменении политики | Сложная ментальная модель                        |
| Per-field override (гранулярный контроль) | Клиент делит владение полями с Policy            |
|                                           | Неявный apply при каждом сохранении              |

### Вариант B: Policy как шаблон (copy-on-apply, без наследования)

```
Policy (шаблон) ──► явный batch-apply копирует значения в Client
```

Никакого `inherited_from_policy`. Apply — явное действие. После применения Client полностью владеет полями. Policy — просто сохранённый пресет.

| Плюсы                                        | Минусы                               |
|----------------------------------------------|--------------------------------------|
| Client — единственный владелец полей         | Нет авто-синхронизации               |
| Ментальная модель проще: шаблон → применил   | При изменении политики — ручной re-apply |
| Нет конфликта «кто владеет полем»            |                                      |
| Не нужен override/returnToPolicy             |                                      |
| Меньше полей в Client (нет `inherited_from`) |                                      |

### Вариант C: Настройки на Group (без отдельной таблицы Policy)

```
ClientGroup { totalGB, expiryDays, limitIP, inboundIds } ──► Client наследует
```

Группа сама хранит настройки. Policy как отдельная таблица не нужна.

| Плюсы                                     | Минусы                                    |
|-------------------------------------------|-------------------------------------------|
| Два уровня вместо трёх                    | Нельзя переиспользовать настройки         |
| Естественная модель: «настройки группы»   | Дублирование данных между группами        |
| Нет отдельной страницы Policies           | Группа раздувается ответственностью       |

### Вариант D: Policy как пресет с явным apply

```
Policy (пресет в БД) ──► явный apply на группу ──► batch-update Client
```

Policy хранится в БД (переиспользование), но без наследования. Apply — всегда ручной и явный.

| Плюсы                                   | Минусы                             |
|-----------------------------------------|------------------------------------|
| Переиспользование между группами        | Нет авто-синхронизации             |
| Явное действие = предсказуемость        |                                    |
| Client — хозяин своих полей             |                                    |
| Нет `inherited_from_policy`             |                                    |

### Вариант E: Batch-edit без Policy (минималистичный)

Никаких Policy. Никакого наследования. Группы — только для организации/фильтрации. Выбрал N клиентов → применил изменения массово.

| Плюсы                                        | Минусы                                |
|----------------------------------------------|---------------------------------------|
| Максимальная простота                        | Нет переиспользования                 |
| Client — абсолютный владелец                 | Ручная работа при каждом изменении    |
| Ноль новых таблиц                            | Не масштабируется на сотни клиентов   |

## 5. Рекомендация

**Вариант B (Policy как шаблон, copy-on-apply)** — оптимальный баланс между «не перетягивать одеяло с Client» и «удобно управлять сотнями клиентов»:

1. Policy остаётся как сохранённый шаблон (переиспользование между группами)
2. Убирается поле `inherited_from_policy` — Client всегда владеет своими полями
3. Apply — явное действие с preview: «будет затронуто N клиентов в M группах»
4. После apply поля скопированы в Client — никакой персистентной связи
5. Изменил Policy → жмёшь «Re-apply» явно
6. Трёхуровневый индирекшн и конфликт владения полями исчезают

**Что теряем:** авто-синхронизацию. Но она же и создаёт главные UX-проблемы текущего решения.

---

## 6. Ближайшие улучшения без смены архитектуры

Если модель не трогаем, можно исправить UX точечно:

1. **Вынести привязку Policy из модалки Rename** — отдельная кнопка/модалка «Assign Policy» на строке группы
2. **Разделить «Save Policy» и «Apply Policy»** — на PoliciesPage добавить явную кнопку Apply с preview затронутых клиентов
3. **Показывать clientCount на PoliciesPage** — не только `groupCount`, но и суммарное количество клиентов под политикой
4. **Встроить override/returnToPolicy в форму редактирования клиента** — рядом с каждым наследуемым полем показывать статус (inherited/overridden) и переключатель
