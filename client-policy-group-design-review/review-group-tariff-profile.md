# Design Review: Group / Tariff / Profile

**Дата:** 2026-08-01
**Рецензия на:** `design-group-tariff-profile.md`

---

## Общая архитектура — сильная сторона

Трёхслойная модель **Profile → Tariff → Group → Client** — хороший выбор. Разделение «кирпичей настроек» (Profile) и «композиций» (Tariff) даёт переиспользование без дублирования. Это типичный паттерн *policy composition*, и он здесь уместен.

---

## Слабые места и риски

### 1. Сложность ментальной модели

Три сущности + стратегии наложения (overwrite / sum / union / restrict) + override-ы на клиенте = **когнитивная нагрузка для оператора**. Типичный вопрос при отладке: «Почему у клиента 600 GB?» — ответ требует обхода всей цепочки. 

- В UI видна попытка это компенсировать (resolved preview в модалке), но это только в одном месте. Нет глобального «Effective values» view для клиента на странице Clients.
- Рекомендация: добавить эндпоинт / UI-элемент, показывающий **разбор по шагам** — какой профиль какое значение дал и какая стратегия победила.

### 2. Nullable-семантика: NULL vs 0

Различие `NULL` («не высказывается») и `0` (unlimited) — **классический источник багов**. В коде это будет работать, но:

- Любой `omitempty` в JSON-сериализации сольёт `NULL` и `0` в `0`. Нужна явная типизация через `*int64` в Go + кастомная сериализация.
- В API-схемах это легко пропустить — фронтенд может отправить `0` вместо `null` при пустом поле.
- Рекомендация: зафиксировать в OpenAPI-схеме strict nullable через `type: integer, nullable: true` и валидировать на фронте через Zod.

### 3. Стратегии на уровне tariff, а не per-field

Стратегии `traffic_strategy` и `inbound_strategy` хранятся на тарифе, но `expiry_days` и `limit_ip` всегда overwrite. Это **асимметрия**:

- Если завтра понадобится `limitIp_strategy = 'min'` (самое строгое из цепочки), придётся добавлять колонку и миграцию.
- Рекомендация: рассмотреть хранение стратегий как JSON-объект `{traffic, inbounds, limitIp, expiry}` — расширяемо без миграций.

### 4. Position-based ordering в БД

`PRIMARY KEY (tariff_id, profile_id), UNIQUE (tariff_id, position)` — **проблема при swap/insert**. Перестановка профилей требует обновления нескольких строк в транзакции. API `POST /tariffs/:id/profiles` решает это атомарной заменой, но:

- Нет защиты от gaps (позиция 0, 1, 3 без 2).
- Нет защиты от дубликатов на клиентском уровне (только UNIQUE constraint).
- Рекомендация: в сервисном слое валидировать что позиции образуют последовательность `0..N-1`.

### 5. Dead columns в БД

> Старые колонки `tariffs.total_gb, expiry_days, limit_ip, inbound_ids` — исключаются из Go-модели, в БД останутся но не читаются.

Это **скрытый техдолг**. Колонки без data-миграции = данные в БД есть, но логика их не видит. Если оператор заглянет в SQLite через CLI — увидит «потерянные» данные. 

- Рекомендация: добавить data-миграцию (скопировать значения в profile + tariff_profiles) или хотя бы комментарий в `db.go`.

### 6. Удаление `POST /tariffs/:id/apply`

Read-time резолв убирает необходимость явного применения — это хорошо. Но это **breaking change** для API-клиентов, которые используют apply для синхронизации. Нужен changelog/note в OpenAPI.

### 7. `restrict` стратегия для inbound-ов

> Пересекаем все non-null inbound_ids; если хотя бы один список пуст после пересечения — результат пуст.

**Потенциальная ловушка**: оператор ставит restrictive профиль первым, потом добавляет новый профиль без `inbound_ids` (NULL) — restrict игнорирует NULL. Но если профиль с пустым списком `[]` попадёт в цепочку — клиент останется без inbound-ов. Разница между NULL и `[]` критична и неочевидна.

### 8. Unit-конверсия (GB ↔ bytes)

> Profile хранит traffic в GB. Эффективное значение вычисляется в bytes (<< 30).

Использование битового сдвига для конверсии — нормально для Go, но:

- В JSON API и UI значения будут в bytes (644245094400), что **нечитаемо**. API `GET /tariffs/:id` возвращает `"traffic": 644245094400` — человеку это бесполезно.
- Рекомендация: в API-ответах отдавать и `bytes` и `displayValue` (600 GB), или в UI всегда форматировать.

### 9. UI — единая страница с тремя вкладками

Три вкладки (Groups / Profiles / Tariffs) на одной странице — **компромисс**. Для малого количества сущностей это удобно, но:

- Profiles и Tariffs — самостоятельные сущности с CRUD. При росте (>50 профилей) вкладки станет тесно.
- «Traffic» в колонке таблицы Groups — это resolved traffic. Непонятно, суммарный или per-client.
- Drag-and-drop в модалке tariff-a — хороший UX-выбор, но нужен drag-handle affordance (☰ есть — хорошо).

---

## Что сделано хорошо

- **Resolved preview** в модалке тарифа — оператор видит итог до сохранения.
- **Защита от удаления** профилей и тарифов при наличии ссылок — с перечнем зависимых.
- **Override-механизм** на клиенте не ломается — совместим с существующим API.
- **Read-time резолв** — устраняет проблему «тариф изменён, но клиенты не обновлены».
- **Dead code cleanup** — явно перечислены удаляемые функции.

---

## Итог

Дизайн **крепкий на уровне данных и бизнес-логики**, но имеет три основных риска:

1. **Сложность отладки** — нужны инструменты для «почему у клиента такое значение?»
2. **NULL vs 0 / NULL vs []** — нужны строгие контракты на всех слоях (Go types, Zod schemas, DB constraints)
3. **Миграция данных** — старые колонки тарифов остались сиротами, это нужно решить до релиза

Фича проектировалась с прицелом на расширяемость (новый профиль → новый тариф → группа), и эта цель достигнута. Цена — возросшая когнитивная нагрузка, которую нужно компенсировать в UI и документации.
